# 鉴权交互 SOP（Agent 执行用）

鉴权不是纯脚本能完成的：**建应用、开隧道、点授权这三件事只有用户能做**。
这份 SOP 规定你（Agent）在每个节点该问什么、该做什么、怎么验证、失败怎么退。

核心原则：**一次只让用户做一件事，每步先验证再进下一步。** 不要一次甩出全套步骤。

---

## 第 0 步：判断要不要走这个流程

只要用户的需求涉及**真实数据**（拓词、搜索量、账户信息、跨账户复制），先跑：

```bash
uv run <skill>/scripts/bmctl.py accounts list
```

| 结果 | 动作 |
|---|---|
| `total > 0` 且 `usable: true` | **直接干活**，不要提鉴权，用户不关心这个 |
| `total: 0` | 走下面的流程 |
| 报 Python 相关错误 | 是环境问题，跳「错误分支 E1」 |

**不要**在不需要数据的时候主动提鉴权，那只是噪音。

---

## 第 1 步：先确认范围，别急着要参数

问一个问题，不要连问三个：

> 你这次要接几个账户？这些账户是同一个百度应用下的，还是分属不同应用？

根据回答分路：

| 回答 | 走 |
|---|---|
| 1 个账户，自己用 | 路径 A（最省事） |
| 多个账户，同一个应用 | 路径 B |
| 多个账户，不同应用 | 路径 B + apps.json |
| 我手上已经有 token | 路径 C |

---

## 第 2 步：收集信息（分组问，按需问）

**永远不要一次要五个字段。** 按下面的顺序，能少问就少问。

### 第一批（所有路径都要）

> 需要两个信息，都在 `dev2.baidu.com` → 应用管理里：
> 一是 **AppID**，二是**开发者 uid**（不是推广账户的 userId，是创建应用那个账号的 uid）。

拿到后如果用户不确定 uid 是哪个，提醒他：应用管理页面里通常标为"开发者ID"或"用户ID"，和推广账户 ID 不是一个东西。

### 第二批（只有在需要自动换令牌时才要）

> 还需要这个应用的 **SecretKey**（应用管理里能看到）。
> 它相当于应用的密码，我只会用它去换令牌，不会写进任何文件或对话记录。

**注意**：拿到 SecretKey 后不要再复述它，日志里也不要打印。

### 第三批（只有走路径 B 才要）

> 最后需要一个**公网可达的回调地址**。你有现成的隧道吗？没有的话我可以带你起一个。

---

## 路径 A：单账户，手工接码

**适合**：就一个账户，懒得起服务。

**步骤**

1. 让用户提供公网回调地址（或用 webhook.site 这类临时接收页）
2. 你生成授权链接：

```bash
uv run <skill>/scripts/bmctl.py auth link --app-id <AppID> \
  --developer-uid <uid> --callback <公网地址> --alias <账户别名>
```

3. 把 `auth_url` 给用户，说清：

> 打开这个链接，点「同意授权」。百度会跳到回调地址，页面上能看到一个 `authCode`，把它复制给我。
> 这个码只能用一次，复制后尽快发我。

4. 拿到 code 立刻换令牌：

```bash
uv run <skill>/scripts/bmctl.py auth exchange --code <authCode> \
  --app-id <AppID> --secret-key <SecretKey> --user-id <userId> \
  --user-name "<账户中文名>" --alias <别名>
```

5. **验证**（不能省）：跳「第 3 步验证」

---

## 路径 B：多账户，起服务

**适合**：多个账户，或要发给别人授权。

**步骤**

1. 确认回调地址。没有隧道就先带用户解决，说清：

> 回调必须公网可达，localhost 不行。你有两种选择：一是我给你命令起 cloudflared 隧道，二是你已有的服务器反代。
> 另外记得把这个地址填到百度应用管理的「回调地址」里，不填百度不会回调。

2. 起服务（**后台跑，别阻塞对话**）：

```bash
uv run <skill>/scripts/bmctl.py auth serve --port 8080 \
  --app-id <AppID> --developer-uid <uid> --secret-key <SecretKey> \
  --wait 900
```

多应用时用 `--apps-file`，格式见 `auth.md` 第五节。

3. 为每个账户生成链接，**逐个**给：

```bash
uv run <skill>/scripts/bmctl.py auth link --app-id <AppID> \
  --developer-uid <uid> --callback <公网地址> --alias rose_shop
```

4. 告诉用户服务在等，以及怎么判断成功：

> 服务已经在 8080 等着了，最长等 15 分钟。你把链接发给对应账户的持有人，对方点「同意授权」后我这边会收到，自动存成对应账户。
> 接完告诉我，或者我这边有输出会告诉你。

5. 收到回调后核对 `alias_source`：
   - `state` → 别名生效，正常
   - `user_id` → 百度覆盖了 state，告诉用户账户名变成了 `acct_<userId>`（见「已知不确定点」）

6. **验证**：跳「第 3 步」

---

## 路径 C：已有 token，直接写文件

**适合**：用户手上已经有一份 accessToken（可能还有 refreshToken）。

1. 只问两件事：**accessToken** 和**账户中文名**。

> 有这个 accessToken 就能直接调，但它在 24 小时后失效。你如果还有 refreshToken，一起给我就能长期用；没有的话明天要重新弄一次。

2. 写凭据文件（macOS/Linux 下权限必须 600；Windows 无 POSIX 权限位，跳过 chmod 即可）：

```bash
# 路径：~/.baidu-marketing/accounts/<alias>.json
# expires_at / refresh_expires_at 是 Unix 时间戳（秒），不确定就写 0
chmod 600 ~/.baidu-marketing/accounts/<alias>.json
```

3. **验证**：跳「第 3 步」

4. 验证完提醒用户：

> 验证通过了。这个 token 贴出来过一次，建议你之后重新授权换一个，旧的会自然失效。

---

## 第 3 步：验证（所有路径都必须做）

```bash
# 1. 账户能识别
uv run <skill>/scripts/bmctl.py accounts list

# 2. 真的能取数
uv run <skill>/scripts/bmctl.py --account <别名> kr expand --seed "测试" --limit 1
```

两条都通过才算接入完成。**只跑第一条就宣布成功是不合格的**——凭据写对了不等于权限够。

## 错误分支

| 现象 | 判断 | 你要说的 |
|---|---|---|
| `89406` | 权限域没开通，**不是令牌坏了** | 「令牌本身是好的，但这个应用没开通该接口对应的权限域。要去开发平台补开，补完需要重新授权一次。」 |
| `81020` | token 与 userName 不匹配 | 「账户名填错了，要用这个令牌所属账户自己的中文名。」 |
| `81012` | 缺 userName | 「还差账户中文名。」 |
| `refresh_expired: true` | 授权超 30 天 | 「授权过期了，需要重新走一次授权，没有别的办法。」 |
| 服务一直等到超时 | 隧道没通 / 后台没填回调地址 / 对方没点 | 按顺序排查，不要笼统说"失败了" |
| `Address already in use` | 端口占用 | 换 `--port 8081` |
| `state 不属于任何已配置应用` | 用了旧链接或 base 对不上 | 重新生成链接，别复用旧的 |

**E1（运行环境问题）**：报 `command not found` 或模块导入失败 → 是环境问题，不是权限问题。先确认 `uv --version` 可用（没有就按 onboarding 的指引装），别往鉴权方向排查。只有绕过 uv 直接用低版本 python 时才会出现退出码 6。

---

## 已知不确定点：state 是否原样回传

多账户靠 `state` 里的别名区分账户。百度**可能**会覆盖掉自定义 state（尚未实证）。

所以：

- 看到 `alias_source: "user_id"` 时，**主动告诉用户**：「百度没有回传自定义别名，账户按 userId 存成了 `acct_xxxxx`，以后用这个名字操作。」
- 不要假装别名生效了

---

## 禁止事项

1. **不要代替用户点授权**。你没有浏览器会话，也不可能代点。
2. **不要编造 AppID、SecretKey、token**。缺什么就问，不要用假值先跑。
3. **不要一次甩全套步骤**。用户会劝退，尤其非技术用户。
4. **不要在对话里复述 SecretKey**。拿到就用，别回显。
5. **不要跳过验证**。`accounts list` 有记录 ≠ 能取数。
6. **不要在没数据时编搜索量/出价**。宁可说「先给框架，接入后再校准」。
7. **不要承诺时间**。审核、权限开通都不由我们控制。
